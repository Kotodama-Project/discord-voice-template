# 運用

起動は`start`、確認は`status`、停止は`shutdown`です。バックグラウンドで動かす場合は、所有者・cwd・PID・起動時刻を持つサービス管理を使ってください。名前の一致だけで他のNodeやBotを止めません。

設定変更は現在の操作者・出典の検査に反映します。音声モデルや接続先、実行先を変える場合は、このインストールを停止してから再起動します。

クラッシュ後のrunning/stoppingはuncertainとして保持し、未確認の仕事を自動再実行しません。自動復旧を使う場合は、serviceのprivate環境へ `KOTODAMA_RUNTIME_DOMAIN` を設定します。この値は同じhost・PID namespace内では再起動後も同じにし、同じデータ領域を見られる別container・別hostでは必ず変えます。lockのdomainが一致し、記録PIDが存在しない場合だけCAS付きで回収します。domainがない旧lock、domain不一致、生存PID、確認不能では起動を拒否します。記録されたPID・起動時刻と実際のプロセスを照合せず、単にlockを削除して二つのwriterを起動しないでください。

作業候補はTaskのrevisionごとのworktreeとartifact directoryに残します。旧候補・会話・出典を削除して復旧しません。モデルが申告したファイル名だけでなく、Gitの実変更から成果物を列挙します。

一つのBotは同じサーバーで一つのVCを使います。このテンプレートの初版は、一つのインストールに一つのVCを設定します。別の通話を勝手に移動して枠を空けません。

`voice.autoJoin: true` では、起動時・入退室時・10秒ごとの確認で、設定したVCへ入退室します。全人間参加者が現在の `participantIds`（または選択した参加者同意方式）に含まれる場合だけ自動接続します。無人になってから15秒以上経過した次の確認で、最後の文字起こしを確定して退出します。途中で人が戻れば退出待ちを取り消します。対象外の人や本人の停止設定を検出した場合は、新しい音声処理・再生を止めて退出します。

`voice pause` は録音を止め、`voice leave` は退出します。どちらも自動接続を停止し、SQLiteに保存した設定を再起動後も保持します。`voice join` または `voice resume` で解除します。聞き役・議事録のモード切替、発話停止、仕事の停止は、この手動停止の設定を解除しません。

一時切断では5秒以内の接続復旧を待ちます。復旧しなければ文字起こしを確定して接続を閉じ、その後の在室確認で再接続できます。利用上限に達した場合は停止設定も保存します。日付変更・再起動・上限値の変更だけで処理を再開せず、残量を確保して明示的に `voice join` / `voice resume` を実行します。

音声APIが残高不足を返した場合は「音声APIの残高補充待ち」と表示して退出し、停止を保存します。発話、在室確認、モード切替、再起動では再試行しません。残高を補充した後、既存の音声利用上限内で `voice join` / `voice resume` を実行します。通常ログには分類したエラーコードだけを記録し、APIの生の診断文や認証情報は出しません。

ローカルASR構成では `voice status` に「ローカル聞き役」または現在のLive会話数を表示します。`LOCAL_ASR_FAILED`、`LOCAL_ASR_BUSY`、`VOICE_UTTERANCE_LIMIT` が続く場合は、新しいLive会話を増やさず、ASR endpointのhealth、処理時間、queueを確認します。ASR失敗時にクラウド文字起こしへ自動で切り替えません。

音声の途切れは `outputPrefillMs` を少し増やし、体感遅延は少し減らして調整します。`maxOutputQueueMs` は古い音声を溜めない上限です。`VOICE_OUTPUT_QUEUE_OVERFLOW` が出た場合はその発話を止め、provider速度、CPU、Discord送信の詰まりを確認します。上限だけを広げて古い音声を後から流しません。

GPT-Liveの利用量は `session.usage.updated` の累積秒を前回値と置き換え、5秒ごとと `session.closed` の最終値を `voice.usage_snapshot` に保存します。snapshot同士を足しません。Luna Responsesはinput、cached input、output、total tokenを応答ごとに一度だけ保存します。人の入力が `voice.conversationIdleSeconds` を超えて途切れた場合はLiveだけを閉じます。長い仕事へ移ったら音声会話を閉じてもworkerは継続でき、結果は次の呼びかけ時に必要な要点だけを再投入できます。

アップデートは、停止→状態保存→新しいソースと固定依存で試験→起動→実際の依頼と成果確認の順です。問題があればコードを前の版へ戻し、データは保持します。

## 既存Botからの移行

上のアップデート手順は互換性を確認した同じ製品内の更新用です。別の稼働版からは、既存設定のキーを削るだけで移行しません。まず別のデータ領域で候補を検証します。旧DBのコピーを新しい `dataDir` へ置くだけの移行も未対応です。

現行版は個人DMへの文字起こし・成果配送、明示した参加者、チャンネル別の文脈を使います。共有会議Botの後継にする場合は、次を同じ実利用経路で確認してください。

1. 対象Bot・VC・テキスト共有先・操作者・作業先を固定し、共有先で読める人と元発話の閲覧範囲を照合する。参加者の入退室と本人の停止設定を、録音時・後処理時・配送時で確認する。
2. VCの発話と仕事部屋での訂正を同じ仕事へ結び、資料を読める範囲を越えて文脈や成果を共有しない。現在のチャンネル別文脈を、共有会議の継続として受け入れない。
3. 旧記録・実行中/停止中の仕事・送信結果不明の配送・会議の配送待ちを分類する。原文、版、閲覧範囲、実行参照、配送先を保ち、未処理という理由だけで再実行・再送しない。旧ownerと新ownerに同じ依頼を書き込まない。
4. 旧sourceと設定の固定版、録音とDBの整合した退避、復旧手順を確認する。2人の実VCで発話・訂正・実行・停止・成果返送を確認してから、対象入口だけを切り替える。

`STORE_MIGRATION_REQUIRED` は、既知の旧拡張テーブルや非対応の仕事状態を検出したための起動拒否です。新Storeのスキーマ更新・実行状態の復旧前に止まります。エラーを回避するためにテーブルや行を削除しないでください。これは既知の非互換を防ぐ検査で、通過しても全ての旧データが移行可能という意味ではありません。

共有会議への対応は[製品Issue #3](https://github.com/Kotodama-Project/discord-voice-template/issues/3)、既存データ・サービス・切戻しは[移行Issue #442](https://github.com/Kotodama-Project/Kotodama-project/issues/442)で追跡します。イベント連携や汎用の自律実行機構は、この移行のために一括で復活させません。

音声はDiscordの入力アカウントごとに扱います。共有マイクなど本人を特定できない入力は `discord.unattributedUsers` へ登録し、話者不明として記録します。その発言からは自動実行・音声回答を始めません。重なった別アカウントの入力は別トラックです。

一回だけの音声確認枠は `voice.maxTotalAudioSeconds` に累計上限を設定します。日次上限とは別に、日付や再起動をまたいでも同じ累計で停止します。聞き取り接続と回答用接続が同じ枠を消費し、原音は保存しません。説明・同意確認は人間側の運用責任で扱い、Botは確認を繰り返しません。`participant_opt_in`を選んだ場合だけ、説明の版に紐づく参加者記録を利用します。
